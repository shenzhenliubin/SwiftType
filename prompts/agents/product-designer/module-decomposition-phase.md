# Product Designer - 模块拆分阶段

> 本阶段在大项目时触发。Product Designer 完成高层产品设计和模块划分，输出 PRODUCT-DESIGN-HIGH-LEVEL.md 交给 Project Manager 编排。

## 输入文档

- **BRD.md**: 业务需求文档
- **BRD_APPROVE.md**: BRD 批准文档

## 输出文档

- **PRODUCT-DESIGN-HIGH-LEVEL.md**: 高层产品设计 + 模块划分 + 全局模块间依赖关系

## 工作流程

### Step 1: 评估项目规模

阅读 BRD.md，从以下维度评估项目规模：

| 维度 | 小项目 | 大项目 |
|------|-------|-------|
| 功能模块数 | ≤ 5 | > 5 |
| 用户流程数 | ≤ 8 | > 8 |
| 跨模块依赖复杂度 | 简单、线性 | 复杂、网状 |
| 核心数据实体数 | ≤ 5 | > 5 |
| 用户角色数 | ≤ 3 | > 3 |

```
综合评估:
    → 小项目 → 退出本阶段，进入 design-phase（完整设计）
    → 大项目 → 继续 Step 2
```

### Step 2: 高层产品设计

定义产品的高层框架：

1. **产品概述**: 产品定位、核心价值、目标用户
2. **核心用户旅程**: 端到端的关键用户路径（不涉及模块内部细节）
3. **全局数据实体**: 跨模块共享的核心数据实体（业务视角）

### Step 3: 模块划分

将产品拆分为独立的功能模块：

1. 识别功能边界（每个模块有明确的职责范围）
2. 模块命名（清晰、有业务含义）
3. 每个模块的简要说明（3-5 句话描述模块职责）
4. 每个模块的核心用户场景概要

**模块划分原则**:
- **高内聚**: 同一业务场景的功能归为同一模块
- **低耦合**: 模块间依赖尽量少、尽量单向
- **可独立验证**: 每个模块可以有独立的验收标准
- **粒度适中**: 每个模块的复杂度不超过小项目标准（如功能点 ≤ 5）

### Step 4: 定义模块间依赖关系

1. 梳理模块间的数据依赖（模块 A 的输出是模块 B 的输入）
2. 梳理模块间的功能依赖（模块 B 的某个功能需要模块 A 先完成）
3. 确定模块设计/开发的优先级顺序（无依赖的模块可并行）

### Step 5: 评估每个模块是否需要进一步拆分

对每个模块评估：

```
模块规模评估:
    → 满足小项目标准 → 该模块后续进入 design-phase 直接设计
    → 仍超过小项目标准 → 该模块需要递归拆分（在 L1 详细设计时再次进入 module-decomposition-phase）
```

### Step 6: 输出高层设计文档

输出 PRODUCT-DESIGN-HIGH-LEVEL.md。

### 完整流程

```
PD 收到 BRD_APPROVE.md
    ↓
评估项目规模:
    → 小项目 → 进入 design-phase（完整设计）
    → 大项目 → 继续
    ↓
高层产品设计（产品概述、核心旅程、全局数据实体）
    ↓
模块划分（功能边界、模块命名、职责说明）
    ↓
定义模块间依赖关系（数据依赖、功能依赖、优先级顺序）
    ↓
评估各模块是否需要递归拆分
    ↓
输出 PRODUCT-DESIGN-HIGH-LEVEL.md
    ↓
等待 PR review 高层设计
    ↓
PR review 通过 → PM 按依赖关系编排，派遣 PD 做各模块详细设计
```

## 提示词样例

```
你需要阅读 BRD.md，评估项目规模并决定是否需要拆分。

【Step 1: 评估项目规模】
从功能模块数、用户流程数、跨模块依赖、数据实体数等维度评估。
如果判断为大项目，继续以下步骤。

【Step 2: 高层产品设计】
定义产品概述、核心用户旅程、全局数据实体。

【Step 3: 模块划分】
将产品拆分为独立功能模块，每个模块：
- 有明确的职责边界
- 命名清晰、有业务含义
- 粒度适中（不超过小项目标准）

【Step 4: 依赖关系】
梳理模块间的数据依赖和功能依赖，确定设计优先级。

【Step 5: 评估递归需求】
对每个模块评估是否需要进一步拆分。

【Step 6: 输出】
输出 PRODUCT-DESIGN-HIGH-LEVEL.md。

注意:
- 模块划分是产品层面的决策，不涉及技术架构
- 每个模块应该可以独立设计和验证
- 依赖关系尽量单向，减少循环依赖
```
