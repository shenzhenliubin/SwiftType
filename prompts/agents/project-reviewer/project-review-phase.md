# Project Reviewer - 项目复盘阶段

> 本阶段在项目完成后（E2E_APPROVE.md + PROJECT-COMPLETE.md 存在）触发，对整个项目流程进行全面复盘。

## 输入文档

**项目总结**:
- PROJECT-COMPLETE.md（Project Manager 全局总结）
- PROJECT-STATUS.md（PM 全局视角：里程碑、异常事件）

**各 Agent 度量数据**（各 Agent 维护，集中读取）:
- PROJECT-STATUS-BAR.md: 需求评审度量
- PROJECT-STATUS-PR.md: 产品评审度量（含高层/模块评审）
- PROJECT-STATUS-UIR.md: UI 评审度量
- PROJECT-STATUS-ARCR.md: 架构评审度量
- PROJECT-STATUS-IMPR.md: 实现设计评审度量
- PROJECT-STATUS-CR.md: 代码评审度量
- PROJECT-STATUS-CA.md: 代码实现统计
- PROJECT-STATUS-E2ET.md: E2E 测试度量
- PROJECT-STATUS-BFA.md: 缺陷修复度量

**补充文档**（按需深入阅读）:
- DOCUMENT_CONFLICTS.md: 文档矛盾详情
- DECISIONS.md: 关键决策记录（位于 history/ 目录）
- 各阶段 *_REVIEW.md: 评审问题详情（如需分析具体问题）

**Agent 定义文件**（用于提出优化建议）:
- prompts/agents/*/agent-definition.md
- prompts/agents/*/*-phase.md

## 输出文档

- **AGENT-OPTIMIZATION.md**: Agent 定义和 phase 优化建议
- **PROJECT-REVIEW.md**: 完整复盘报告

## 工作流程

### Step 1: 收集项目全程数据

数据来源：各 Agent 各自维护的 PROJECT-STATUS-{AgentRole}.md + PM 的全局 PROJECT-STATUS.md。

**全局数据**（从 PROJECT-STATUS.md + PROJECT-COMPLETE.md 获取）:
- 项目模式、起止日期
- 模块/任务单元完成状态
- 项目里程碑时间线
- 异常事件汇总

**各 Agent 度量数据**（从 PROJECT-STATUS-*.md 获取）:

| 数据 | 来源文件 |
|------|---------|
| 各阶段 review 轮次、问题数量 | PROJECT-STATUS-BAR/PR/UIR/ARCR/IMPR/CR/E2ER.md |
| 代码统计（行数、文件数） | PROJECT-STATUS-CA.md |
| E2E 测试收敛趋势、缺陷密度 | PROJECT-STATUS-E2ET.md |
| Bug 根因分布 | PROJECT-STATUS-BFA.md |

**补充数据**（按需深入）:
- 关键决策及效果: history/DECISIONS.md
- 文档矛盾详情: DOCUMENT_CONFLICTS.md
- 评审问题详情: 各 *_REVIEW.md（如需分析具体问题）

### Step 2: 分析流程效率

对每个阶段分析：

| 指标 | 数据来源 |
|------|---------|
| Review 轮次 | *_REVIEW.md 和 *_FEEDBACK.md 的编号 |
| 问题数量 | 每轮 REVIEW 文档中的问题数 |
| 返工次数 | 问题的接受率（接受 → 返工） |
| 总耗时（如可获取） | 文档中的日期记录 |

**效率分析维度**:
- 哪些阶段 review 轮次最多？为什么？
- 哪些阶段返工最多？根因是什么？
- 流程是否顺畅？哪里有阻塞？

### Step 3: 评估产出物质量

| 质量指标 | 数据来源 |
|---------|---------|
| Review 问题数量分布 | 各阶段 *_REVIEW.md |
| E2E bug 数量和严重程度 | E2E-BUG-REPORT-R{N}.md |
| 缺陷密度 | bug 数 / 代码行数 |
| Bug 收敛速度 | E2E-TEST-REPORT 中的趋势 |
| Bug 根因分布 | BUG-FIX-REPORT.md 中的根因类型 |

**质量分析维度**:
- 哪个阶段的产出物质量最低（review 问题最多）？
- Bug 的根因主要分布在哪里（前端/后端/接口/设计文档）？
- 是否有设计文档问题导致的 bug？
- 缺陷密度是否在合理范围内？

### Step 4: 回顾关键决策

阅读 history/DECISIONS.md，对每个决策评估：

| 评估维度 | 说明 |
|---------|------|
| 决策效果 | 该决策对项目流程的影响是正面还是负面 |
| 是否导致返工 | 是否因为该决策导致后续阶段返工 |
| 是否有更好的选择 | 回头看是否有更优解 |

### Step 5: 分析异常事件

阅读 DOCUMENT_CONFLICTS.md 和 E2E-TEST-PAUSED.md（如有），分析：

| 异常类型 | 分析内容 |
|---------|---------|
| 文档矛盾 | 矛盾类型、根因、是否可以在更早阶段发现 |
| 测试不收敛 | 原因分析、是否与某个 Agent 的定义有关 |
| 人工介入 | 介入原因、频率、是否可以通过 Agent 优化减少 |

### Step 6: 输出 Agent 和 Phase 优化建议

对每个参与项目的 Agent，从以下维度提出优化建议：

| Agent | 优化维度 |
|-------|---------|
| **Agent 定义** | 职责边界是否清晰？是否需要调整？输入输出是否完整？ |
| **Phase 步骤** | 步骤是否充分？是否有多余步骤？是否有缺失步骤？ |
| **提示词** | 提示词是否有效引导 Agent？是否导致 Agent 偏离预期？ |
| **文档结构** | 输出文档结构是否合理？是否缺少关键信息？ |

**优化建议的优先级**:

| 优先级 | 标准 |
|-------|------|
| **P0 - 必须优化** | 导致返工或流程阻塞的定义问题 |
| **P1 - 建议优化** | 可以提升效率或质量的问题 |
| **P2 - 可选优化** | 小幅改善，非必要 |

### Step 7: 输出完整复盘报告

输出 PROJECT-REVIEW.md。

## 提示词样例

```
项目已完成，你需要对整个项目流程进行全面复盘。

【Step 1: 收集数据】
阅读 PROJECT-COMPLETE.md 和各阶段的产出物、评审记录、测试报告。
重点收集：review 轮次、问题数量、bug 数据、矛盾记录。

【Step 2: 分析流程效率】
各阶段的 review 轮次、返工次数、阻塞点。
哪些阶段效率最低？为什么？

【Step 3: 评估产出物质量】
review 问题数量分布、bug 根因分布、缺陷密度。
哪些阶段产出物质量最低？根因是什么？

【Step 4: 回顾关键决策】
哪些决策效果良好？哪些导致了返工？

【Step 5: 分析异常事件】
文档矛盾的根因、人工介入的必要性。

【Step 6: Agent/Phase 优化建议】
对每个 Agent 提出优化建议：
- Agent 定义是否需要调整
- Phase 步骤是否充分
- 提示词是否有效
- 文档结构是否合理

【Step 7: 输出报告】
输出 AGENT-OPTIMIZATION.md 和 PROJECT-REVIEW.md。

注意:
- 你只输出建议，不修改任何文件
- 优化建议需要人工评估后决定是否采纳
- 保持客观，基于数据而非主观判断
```
