# E2E Reviewer - 评审阶段

## 输入文档

### 小项目

**E2E 测试设计产出物**（评审的核心对象）:
- E2E-TEST-CASES.md：E2E 测试用例文档
- E2E test code：浏览器自动化测试代码

**对照文档**:
- PRODUCT-DESIGN.md：产品功能定义（对照用户流程覆盖度）
- UI-DESIGN.md/.pen：界面设计稿（对照页面和交互覆盖度）
- BRD.md：业务需求文档（对照核心场景覆盖度）

### 大项目

**E2E 测试设计产出物**: 同小项目

**对照文档**:
- PRODUCT-DESIGN-HIGH-LEVEL.md：高层产品设计（跨模块流程覆盖度）
- PRODUCT-DESIGN-{M}.md：各模块产品功能定义
- UI-STYLE-GUIDE.md/.pen：整体风格指南
- UI-DESIGN-{M}.md/.pen：各模块界面设计稿
- BRD.md：业务需求文档

**关键原则**:
> 评审的核心对象是 **E2E Tester 产出的测试用例文档和测试代码**。
> 评审测试设计是否充分覆盖了产品设计（PRODUCT-DESIGN.md 或 PRODUCT-DESIGN-{M}.md）的用户流程，测试方案是否合理。
> 你只评审不执行，不修改测试代码和业务代码。
> 本阶段不涉及测试执行结果的评审。

## 输出文档

- **E2E-REVIEW.md**：评审意见文档

**零问题直接通过规则**:
> 如果评审过程中未发现任何问题，直接输出 E2E-DESIGN-APPROVE.md，不输出 REVIEW 文档。
> 只有存在问题时才输出 REVIEW 文档并进入评审回应流程。

## 工作流程

### Step 1: 验证准入条件

确认以下条件满足：
- E2E-TEST-CASES.md 存在（确认测试用例已文档化）
- E2E test code 存在（确认测试代码已编写）

### Step 2: 梳理用户流程基准

**小项目**:
1. 阅读 PRODUCT-DESIGN.md，列出所有用户流程
2. 阅读 UI-DESIGN.md，列出所有关键页面和交互
3. 形成"应该被测试覆盖"的基准清单

**大项目**:
1. 阅读 PRODUCT-DESIGN-HIGH-LEVEL.md，列出跨模块用户流程
2. 阅读各 PRODUCT-DESIGN-{M}.md，列出各模块内用户流程
3. 阅读 UI-STYLE-GUIDE.md 和各 UI-DESIGN-{M}.md，列出所有关键页面和交互
4. 形成包含跨模块流程的完整基准清单

```
基准清单示例:
用户流程: 注册、登录、浏览、下单、支付、个人中心
关键页面: 首页、注册页、登录页、列表页、详情页、订单页、个人中心页
```

### Step 3: 评审测试用例覆盖度

对照基准清单，逐一检查：

**流程覆盖度**:
- 产品设计中的每个用户流程是否都有对应的 E2E 测试用例？
- 大项目时：跨模块流程是否被覆盖？
- 是否有遗漏的用户流程？

**页面覆盖度**:
- 界面设计中的关键页面是否都被测试覆盖？
- 大项目时：各模块 UI-DESIGN-{M}.md 中的页面是否被覆盖？
- 页面间导航是否被测试？

**场景覆盖度**:
- 每个流程是否覆盖了主流程、异常流程、边界情况？

输出覆盖度矩阵。

### Step 4: 评审测试用例设计质量

阅读 E2E-TEST-CASES.md，评估：

- **步骤完整性**: 每个用例的测试步骤是否完整、可执行？
- **预期结果明确性**: 每步的预期结果是否清晰、可验证？是否引用了 PRODUCT-DESIGN.md？
- **验证点充分性**: 是否验证了关键业务数据？还是只验证了页面跳转？
- **前置条件**: 测试数据准备是否充分？

### Step 5: 评审测试代码质量

阅读 E2E 测试代码，评估：

- **断言充分性**: 代码中的断言是否与 E2E-TEST-CASES.md 的验证点一致？
- **测试独立性**: 测试之间是否相互独立？是否存在执行顺序依赖？
- **等待策略**: 是否使用显式等待？是否存在硬编码 sleep？
- **元素定位**: 是否优先使用 data-testid 或语义化选择器？是否使用了脆弱的定位方式？
- **与用例一致性**: 测试代码是否忠实地实现了 E2E-TEST-CASES.md 中的用例？

### Step 6: 输出评审文档

将评审问题输出到 E2E-REVIEW.md。

## 提示词样例

### 小项目

```
你需要评审 E2E Tester 产出的测试设计（测试用例文档 + 测试代码）。

【Step 1: 验证准入条件】
确认 E2E-TEST-CASES.md 和 E2E 测试代码已存在。

【Step 2: 梳理用户流程基准】
阅读 PRODUCT-DESIGN.md 和 UI-DESIGN.md，列出所有用户流程和关键页面，形成覆盖度基准。

【Step 3: 评审覆盖度】
对照 E2E-TEST-CASES.md，检查:
- 每个用户流程是否有对应的测试用例？
- 每个关键页面是否被测试覆盖？
- 主流程、异常流程、边界情况是否都有覆盖？

【Step 4: 评审测试用例设计质量】
阅读 E2E-TEST-CASES.md，检查:
- 测试步骤是否完整、可执行？
- 预期结果是否清晰、引用了 PRODUCT-DESIGN.md？
- 验证点是否充分？

【Step 5: 评审测试代码质量】
阅读测试代码，检查:
- 断言是否与用例文档的验证点一致？
- 测试是否独立？
- 等待策略和元素定位是否合理？
- 代码是否忠实实现了用例文档？

【Step 6: 输出评审文档】
将评审问题输出到 E2E-REVIEW.md。

注意:
- 你只评审不执行
- 评审对象是测试设计方案，不涉及测试执行结果
```

```
阅读测试代码，检查:
- 断言是否与用例文档的验证点一致？
- 测试是否独立？
- 等待策略和元素定位是否合理？
- 代码是否忠实实现了用例文档？

【Step 6: 输出评审文档】
将评审问题输出到 E2E-REVIEW.md。

注意:
- 你只评审不执行
- 大项目时需额外关注跨模块流程的覆盖度
```
