# Bug Fix Agent - 缺陷修复阶段

## 输入文档

**缺陷报告**:
- E2E-BUG-REPORT-R{N}.md：当前轮次的缺陷报告（包含复现步骤、预期/实际结果）

**参考文档**:
- E2E-TEST-CASES.md：E2E 测试用例（了解测试预期）
- PRODUCT-DESIGN.md：产品功能定义（确认预期行为）
- API-SPEC.md：接口规范（定位接口问题）
- FRONTEND-DESIGN.md：前端详细设计（定位前端问题）
- BACKEND-DESIGN.md：后端详细设计（定位后端问题）
- ARCHITECTURE.md：技术架构（了解整体结构）

## 输出文档

- **BUG-FIX-REPORT.md**：修复报告（修复内容、影响范围、验证结果）
- **修复后的业务代码**：前端/后端代码修改
- **PROJECT-STATUS-BFA.md**：Bug Fix Agent 度量数据（每轮修复完成时追加）

## 工作流程

### Step 1: 确认前置条件

确认以下条件满足：
- E2E-BUG-REPORT-R{N}.md 存在（有缺陷需要修复）
- 系统环境就绪（前端 + 后端服务可访问）
- 相关代码可访问（已集成到主分支）

### Step 2: 阅读缺陷报告

1. 阅读 E2E-BUG-REPORT-R{N}.md
2. 理解每个缺陷的：
   - 复现步骤
   - 预期结果（来自 PRODUCT-DESIGN.md）
   - 实际结果
   - 严重程度
   - 关联的 E2E 测试用例编号
   - 可能涉及的任务单元

### Step 3: 定位缺陷根因

对每个缺陷，对照设计文档定位根因：

```
1. 重新复现缺陷（按缺陷报告中的复现步骤）
2. 对照 PRODUCT-DESIGN.md 确认预期行为
3. 对照 API-SPEC.md / FRONTEND-DESIGN.md / BACKEND-DESIGN.md 定位偏差
4. 确定根因类型
```

根因判断逻辑：

| 根因类型 | 判断依据 | 处理方式 |
|---------|---------|---------|
| **前端代码问题** | 代码行为与 FRONTEND-DESIGN.md 不一致 | 修改前端代码 |
| **后端代码问题** | 代码行为与 BACKEND-DESIGN.md 不一致 | 修改后端代码 |
| **接口实现问题** | 代码行为与 API-SPEC.md 不一致 | 修改对应端代码 |
| **设计文档问题** | E2E 测试预期与 PRODUCT-DESIGN.md 一致，但设计文档定义有误 | 暂停，通知 Project Manager → 人工介入 |
| **测试用例问题** | 缺陷报告与 PRODUCT-DESIGN.md 不一致 | 反馈给 E2E Reviewer 评估 |

> **重要**: 发现设计文档问题或测试用例问题时，不自行修改设计文档或测试代码，而是暂停修复，通知 Project Manager 人工介入。

### Step 4: 修复缺陷

对每个代码层面的缺陷：

1. 制定修复方案（最小化修改范围，不引入新功能）
2. 修改代码
3. 确保修改符合项目编码规范

**修复原则**:
- 只修复缺陷，不添加新功能
- 最小化修改范围，降低引入新问题的风险
- 如果一个修复影响多个缺陷，在报告中说明关联关系

### Step 5: 本地验证

修复完成后，逐项验证：

1. **运行相关单元测试**: 确保修改不破坏已有单元测试
2. **运行相关集成测试**: 确保修改不破坏已有集成测试
3. **运行触发缺陷的 E2E 测试**: 验证缺陷是否已修复

验证结果处理：

```
全部通过 → 进入 Step 6
有新增失败 → 回退修改，重新分析根因，回到 Step 4
原有失败仍未通过 → 重新分析根因，回到 Step 4
```

### Step 6: 输出修复报告

输出 BUG-FIX-REPORT.md，包含：
- 修复的缺陷列表及对应根因分析
- 修改的文件和内容说明
- 影响范围分析
- 本地验证结果

同时更新 PROJECT-STATUS-BFA.md，追加本轮修复的度量数据（修复缺陷数、根因分布）。

### 完整流程

```
阅读 E2E-BUG-REPORT-R{N}.md
    → 逐一分析每个缺陷
    → 定位根因:
        → 代码问题 → 修复 → 本地验证 → 通过 → 输出 BUG-FIX-REPORT.md → CR 评审
        → 代码问题 → 修复 → 本地验证 → 失败 → 回退 → 重新分析 → 修复
        → 设计文档问题 → 暂停 → 通知 Project Manager → 人工介入
        → 测试用例问题 → 暂停 → 反馈 E2E Reviewer
    → BUG-FIX_APPROVE.md → 交给 E2E Tester 重新执行全部测试（regression-phase）
```

### Step 7: Code Review 评审

输出 BUG-FIX-REPORT.md 后，进入 Code Review 闭环：

```
BUG-FIX-REPORT.md → Code Reviewer 评审 → BUG-FIX_REVIEW.md
    → BFA 回应 → BUG-FIX_REVIEW_FEEDBACK.md
    → CR 通过 → BUG-FIX_APPROVE.md
    → CR 不通过 → BFA 修改 → 重新提交 → 回到 CR 评审
```

**CR 评审范围**: 仅评审修复相关代码（不要求全量评审）。

### Step 8: 等待回归结果并决定下一步

BUG-FIX_APPROVE.md 后，等待 E2E Tester 重新执行全部测试（第 N+1 轮）。

| 回归结果 | 动作 |
|---------|------|
| E2E_APPROVE.md 已输出 | 修复工作结束 |
| 新的 E2E-BUG-REPORT-R{N+1}.md | 回到 Step 1，阅读新缺陷报告，重新修复 |
| E2E-TEST-PAUSED.md | 测试不收敛，等待 Project Manager 人工介入 |

### 完整循环流程

```
第 N 轮:
  Bug Fix Agent 阅读 E2E-BUG-REPORT-R{N}.md → 修复 → 本地验证 → BUG-FIX-REPORT.md
        ↓
  E2E Tester 执行全部测试（第 N+1 轮）
        ↓
  结果:
      → E2E_APPROVE.md → 修复工作结束
      → E2E-BUG-REPORT-R{N+1}.md → 回到 Step 1（循环）
      → E2E-TEST-PAUSED.md → 等待人工介入
```

## 提示词样例

```
你需要阅读当前项目目录下的 E2E-BUG-REPORT-R{N}.md 文档，这是 E2E Tester 发现的缺陷。

请逐一分析每个缺陷:

【Step 1: 确认前置条件】
确认 E2E-BUG-REPORT-R{N}.md 存在，系统环境就绪。

【Step 2: 阅读缺陷报告】
理解每个缺陷的复现步骤、预期结果、实际结果。

【Step 3: 定位根因】
对照设计文档定位偏差:
- 对照 PRODUCT-DESIGN.md 确认预期行为
- 对照 FRONTEND-DESIGN.md / BACKEND-DESIGN.md / API-SPEC.md 找到偏差点
- 判断根因类型

如果根因是设计文档问题或测试用例问题，不要自行修改，暂停并通知。

【Step 4: 修复缺陷】
最小化修改范围，只修复缺陷不添加新功能。

【Step 5: 本地验证】
- 运行相关单元测试
- 运行相关集成测试
- 运行触发缺陷的 E2E 测试
如有新增失败，回退修改重新分析。

【Step 6: 输出修复报告】
输出 BUG-FIX-REPORT.md。

注意:
- 只修复缺陷，不添加新功能
- 如果发现设计文档本身有问题，暂停修复并通知人工
- 一个修复影响多个缺陷时，在报告中说明关联关系
- 修复完成后等待 E2E Tester 重新测试，收到新的 bug report 就回到 Step 1
```
