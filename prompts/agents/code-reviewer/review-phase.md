# Code Reviewer - 评审阶段

## 输入文档（阅读所有已确定的产出物）

### 小项目

**任务单元文档**:
- TASK_UNIT_{name}_CODING_COMPLETE.md：任务单元完成信号
- TASK-UNIT-{name}.md：任务单元定义

**代码文件**:
- 前端代码文件：组件代码、状态管理代码、API 调用代码
- 后端代码文件：API 实现代码、业务逻辑代码
- 测试代码文件：API 测试、前端测试、后端测试代码

**设计文档**:
- API-SPEC.md：接口详细规范
- FRONTEND-DESIGN.md：前端详细设计
- BACKEND-DESIGN.md：后端详细设计
- TEST-CASES-API.md：API 测试用例
- TEST-CASES-FRONTEND.md：前端测试用例
- TEST-CASES-BACKEND.md：后端测试用例

**架构和产品文档**:
- ARCHITECTURE.md：技术栈选型
- PRODUCT-DESIGN.md：产品功能定义

**批准文档**:
- IMPLEMENTATION_APPROVE.md：详细设计批准文档

### 大项目

**任务单元文档**:
- TASK_UNIT_{name}_CODING_COMPLETE.md：任务单元完成信号
- TASK-UNIT-{name}.md：任务单元定义

**代码文件**: 同小项目

**设计文档**（模块级）:
- API-SPEC-{M}.md：模块接口详细规范
- FRONTEND-DESIGN-{M}.md：模块前端详细设计
- BACKEND-DESIGN-{M}.md：模块后端详细设计
- TEST-CASES-{M}-API.md：模块 API 测试用例
- TEST-CASES-{M}-FRONTEND.md：模块前端测试用例
- TEST-CASES-{M}-BACKEND.md：模块后端测试用例

**架构和产品文档**:
- ARCHITECTURE.md：技术栈选型
- PRODUCT-DESIGN-{M}.md：模块产品功能定义

**批准文档**:
- IMPLEMENTATION-{M}_APPROVE.md：模块详细设计批准文档

## 输出文档

### 场景 1: 任务单元代码评审

- **TASK_UNIT_{name}_CODE_REVIEW.md**: 评审问题文档
- **TASK_UNIT_{name}_CODING_APPROVE.md**: 批准通过文档（零问题时直接输出）

### 场景 2: 缺陷修复代码评审

- **BUG-FIX_REVIEW.md**: 评审问题文档
- **BUG-FIX_APPROVE.md**: 批准通过文档（零问题时直接输出）

**零问题直接通过规则**:
> 如果评审过程中未发现任何问题，直接输出对应的 APPROVE.md，不输出 REVIEW 文档。
> 只有存在问题时才输出 REVIEW 文档并进入评审回应流程。

## 评审模式判断

根据输入信号判断评审模式：

| 输入信号 | 评审模式 | 评审范围 |
|---------|---------|---------|
| TASK_UNIT_{name}_CODING_COMPLETE.md | 任务单元评审 | 全量代码评审 |
| BUG-FIX-REPORT.md | 缺陷修复评审 | 仅评审修复相关代码 |

## 工作流程

### 场景 1: 任务单元代码评审

#### Step 1: 验证准入条件

确认以下条件满足：
- TASK_UNIT_{name}_CODING_COMPLETE.md 存在
- 测试通过率 100%
- 测试覆盖率 80%+

#### Step 2: 阅读所有文档

阅读以下文档理解设计要求：
- ARCHITECTURE.md：技术栈选型
- API-SPEC.md（或 API-SPEC-{M}.md）：接口规范要求
- FRONTEND-DESIGN.md（或 FRONTEND-DESIGN-{M}.md）：前端设计要求
- BACKEND-DESIGN.md（或 BACKEND-DESIGN-{M}.md）：后端设计要求
- TEST-CASES-*.md：测试用例要求
- PRODUCT-DESIGN.md（或 PRODUCT-DESIGN-{M}.md）：产品功能定义

#### Step 3: 检查文档一致性

在评审代码前，检查文档之间是否有矛盾：
- API-SPEC.md 与代码是否一致？
- 设计文档与代码是否一致？
- 如果发现矛盾 → 在评审问题中标记为"需要人工介入"

#### Step 4: 评审代码

逐一评审各个维度：
- 代码质量、测试覆盖、测试质量
- 前端/后端/API 测试用例一致
- 安全性、最佳实践、性能
- 与设计一致、与接口一致

#### Step 5: 输出评审文档

将评审问题输出到 TASK_UNIT_{name}_CODE_REVIEW.md。

### 场景 2: 缺陷修复代码评审

#### Step 1: 验证准入条件

确认以下条件满足：
- BUG-FIX-REPORT.md 存在
- 修复相关测试通过

#### Step 2: 阅读修复报告

阅读 BUG-FIX-REPORT.md，了解：
- 修复了哪些缺陷
- 修改了哪些文件
- 根因分析和影响范围

#### Step 3: 评审修复代码

仅评审修复相关代码（不要求全量评审），重点关注：
- 修复是否正确解决了缺陷
- 是否引入新问题
- 是否符合编码规范
- 相关测试是否通过

#### Step 4: 输出评审文档

将评审问题输出到 BUG-FIX_REVIEW.md。

```
- 测试代码文件：API 测试、前端测试、后端测试代码

- 命名是否规范？

【维度2：测试覆盖】

- 测试是否可重复？

【维度6：API 测试用例一致】

- 是否存在 SQL 注入？
- 是否有敏感信息暴露？
- 输入是否验证？

【维度8：最佳实践】
- 是否遵循编码规范？
- 是否遵循设计模式？

【维度9：性能】
- 是否存在性能问题？
- 是否有不必要的资源消耗？

【维度10：与设计一致】
- 前端实现是否与 FRONTEND-DESIGN.md 一致？
- 后端实现是否与 BACKEND-DESIGN.md 一致？

【维度11：与接口一致】
- API 实现是否与 API-SPEC.md 一致？
- API 调用是否与 API-SPEC.md 一致？

请将评审问题输出到 TASK_UNIT_{name}_CODE_REVIEW.md 文档。
```
